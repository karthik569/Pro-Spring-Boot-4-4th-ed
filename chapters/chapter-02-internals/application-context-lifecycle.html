Spring Boot ApplicationContext Lifecycle

Spring Boot 4.0.6 Spring Framework 7.0.7 Java 21 target / 25 runtime Servlet + Tomcat 11

The ApplicationContext is the container Spring Boot builds and drives at startup. It is not “just dependency injection” — it sequences definition registration, instantiation, proxying, refresh and event publication. The example below traces each phase through the customer project and validates it against a live run.

The six phases

1

Bootstrap — SpringApplication.run()

CustomerApplication.java:14-19

The entry point uses a SpringApplicationBuilder (not the shortcut SpringApplication.run). It prints the banner (bannerMode(CONSOLE) → banner.txt), logs startup info, triggers auto-configuration (@SpringBootApplication), and — because a servlet API is present — creates an AnnotationConfigServletWebServerApplicationContext that also boots the embedded server.

2

Component scan & bean definition registration

@SpringBootApplication · @ConfigurationPropertiesScan · @EnableScheduling

Before any objects exist, the context reads metadata and registers bean definitions (blueprints):

  • @SpringBootApplication scans com.apress.crm.customer for @Component/@Configuration/@RestController.
  • @ConfigurationPropertiesScan discovers CrmProperties (@ConfigurationProperties(prefix = "crm")) and binds application.properties.
  • @EnableScheduling registers infrastructure that later scans for @Scheduled methods.
3

Bean instantiation + dependency injection

constructor injection throughout

Definitions become live singletons and the constructor dependency graph resolves: CustomerRepository → CrmProperties + auto-configured MessageSource → CustomerController (CustomerController.java:19) and CustomerStatsTask. CustomerConfiguration is @Profile("!prod"), so its beans register only when prod is inactive.

4

AOP proxy creation

ControllerLoggingAspect.java:10-24

@Aspect + @Around("execution(* ...CustomerController.*(..))") makes the context wrap CustomerController in a CGLIB proxy. What other beans inject is the proxy, so every call gets latency logging transparently. Spring Boot 4 defaults to CGLIB/byte-buddy proxies.

5

Refresh completes → lifecycle events

CustomerConfiguration.java:17-26

The server is started and singletons fully initialized, so the context publishes ApplicationReadyEvent. The ApplicationListener<ApplicationReadyEvent> bean seeds three sample customers — the canonical “run after the whole context is up” pattern, versus doing work in a constructor.

6

Steady state — post-startup runtime

@Scheduled + HTTP dispatch

Once ready, the long-lived context hosts @Scheduled(fixedRate = 60000) on CustomerStatsTask (runs on the scheduling thread) and serves HTTP through the proxied CustomerController.

Flow at a glance

main() → SpringApplicationBuilder.run()
  → create AnnotationConfigServletWebServerApplicationContext
  → auto-configuration + component scan → register BEAN DEFINITIONS
  → instantiate singletons + resolve constructor DEPENDENCY INJECTION
  → apply AOP → wrap CustomerController in CGLIB proxy
  → finish refresh → start embedded Tomcat server
  → publish ApplicationReadyEvent → CustomerConfiguration seeds data
  → steady state: @Scheduled tasks + serving requests

Engineering insights.
  • Spring Boot 4 initializes proxy beans with CGLIB / byte-buddy by default.
  • Prefer constructor-bound @ConfigurationProperties over @Value for strong typing, testability, and IDE autocomplete.
  • Seed or verify state in an ApplicationReadyEvent listener, not a constructor — the context (and server) is not fully ready inside a constructor.
