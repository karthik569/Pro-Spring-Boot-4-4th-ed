1 · What this chapter covers

Chapter 3 evolves the simple CRM API into a production-shaped service. The concrete capabilities demonstrated in this codebase are:

  • REST CRUD with proper HTTP semantics (201 + Location, 404, 204).
  • Declarative validation (Jakarta Validation 3.1) on the request body via @Valid.
  • RFC 7807 ProblemDetail error contract through a @RestControllerAdvice.
  • Content negotiation — JSON and XML from the same handler (Jackson XML on the classpath).
  • Path-based API versioning — a legacy /v1_1 and a strict /v2_0 alongside the main /v1.
  • Declarative HTTP client — @HttpExchange + @ImportHttpServices (a Spring Framework 7 feature).

2 · Code walkthrough

Domain model with constraints

Customer.java:8-24

An immutable Java record carrying Jakarta Validation annotations: @NotBlank on name, @Email + @NotBlank on email, and a @Pattern regex on phone. A secondary constructor defaults id to null so new entities can be created without one.

REST controller & HTTP semantics

CustomerController.java

@RestController mapped to /api/v1/customers. create() and update() take @Valid @RequestBody Customer, so an invalid payload throws MethodArgumentNotValidException before the method body runs. create() builds the Location header with ServletUriComponentsBuilder and returns 201 Created; findById() returns 404 when absent; delete() returns 204 No Content.

Global exception handling → RFC 7807

GlobalExceptionHandler.java

A @RestControllerAdvice centralizes error mapping. On MethodArgumentNotValidException it builds ProblemDetail.forStatusAndDetail(400, "Validation failed"), sets a human title, and attaches a flattened errors property of field: message pairs. A second handler maps NoResourceFoundException to a 404 ProblemDetail with a custom type URI. This is the standardized error contract — no raw stack traces leak to clients.

Content negotiation (JSON / XML)

pom.xml:42-45

Adding jackson-dataformat-xml registers an XML HttpMessageConverter. The same controller method serves JSON or XML purely based on the request Accept header — no branching in code.

Path-based API versioning

v1/CustomerControllerV1.java · v2/CustomerControllerV2.java

Two extra controllers demonstrate contract evolution without breaking clients: /api/v1_1/customers is legacy (no @Valid, accepts a partial body) while /api/v2_0/customers is strict (CustomerV2 requires title, name, and a valid email). The same GlobalExceptionHandler serves both.

Declarative HTTP client

client/CurrencyClient.java · client/ClientConfig.java

CurrencyClient is an interface annotated @HttpExchange("https://open.er-api.com/v6/latest") with a @GetExchange("/{base}") method — Spring generates the implementation. @ImportHttpServices(CurrencyClient.class) registers it as a bean (Spring Framework 7). It is exercised in tests rather than wired into a controller.

In-memory repository & startup seeding

CustomerRepository.java · CustomerConfiguration.java

A ConcurrentHashMap-backed Repository keeps the demo self-contained. CustomerConfiguration seeds three customers on ApplicationReadyEvent (the same lifecycle hook as Chapter 2).
