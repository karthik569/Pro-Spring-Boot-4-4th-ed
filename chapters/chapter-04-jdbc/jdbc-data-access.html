1 · What this chapter covers

Chapter 4 replaces the in‑memory map from earlier chapters with a real relational store, and shows two ways to talk to it:

  • DataSource + connection pooling — Spring Boot autoconfigures a HikariCP DataSource from spring.datasource.*.
  • Schema initialization — schema.sql runs on startup to create the customer table.
  • Classic data access — JdbcTemplate with a hand‑written RowMapper and positional ? parameters.
  • Modern fluent data access — JdbcClient with named :param binding and automatic row mapping.
  • Environment profiles — H2 in‑memory by default, PostgreSQL under the prod profile.

2 · Code walkthrough

Two repositories, one interface

CustomerRepository.java · JdbcClientCustomerRepository.java · Repository.java

Both classes implement the same Repository<Customer, UUID> contract but use different APIs:

  • CustomerRepository uses JdbcTemplate — query("SELECT * FROM customer WHERE id = ?", rowMapper, id) with positional ? placeholders and an explicit RowMapper.
  • JdbcClientCustomerRepository uses the fluent JdbcClient — .sql("… WHERE id = :id").param("id", id).query(Customer.class).optional() with named parameters and automatic record mapping.

Only the JdbcTemplate variant is wired: CustomerConfiguration declares @Bean CustomerRepository customerRepository(JdbcTemplate). The JdbcClient class has no @Repository/bean registration, so it is a parallel demonstration (and test target), not the live bean.

RowMapper → immutable record

CustomerRowMapper.java

Maps a JDBC ResultSet row to the Customer record, converting the id column with UUID.fromString. This is the classic Spring JDBC mapping contract.

DataSource, pool & schema init

application.properties · application-prod.properties · schema.sql

Default profile points at jdbc:h2:mem:testdb; HikariCP pools connections lazily on first use. schema.sql creates customer with a UUID PRIMARY KEY and email VARCHAR(255) NOT NULL UNIQUE. The prod profile swaps to jdbc:postgresql://localhost:5432/crm and forces spring.sql.init.mode=always.

Upsert‑style save()

CustomerRepository.java:29-57

Because records are immutable, save() generates a UUID when the id is null and inserts; if the id exists it updates, otherwise it inserts the predefined id. Note the read‑then‑write is not wrapped in a transaction (see observations).

Controller & error handling

CustomerController.java · GlobalExceptionHandler.java

The web layer is unchanged from Chapter 3: @Valid + ProblemDetail for request validation. However, the advice only maps validation and not‑found errors — database‑level failures (e.g. the UNIQUE email constraint) fall through to Spring's default error response.

Observations & suggested improvements

  • Unwired JdbcClient repo: JdbcClientCustomerRepository is never registered as a bean, so the fluent API is only exercised in tests. To use it, add a @Bean (and qualify the injection point, since two Repository beans would then compete).
  • No transaction boundary: the deep‑dive text cites @Transactional(rollbackFor = Exception.class), but the code has none; save() does read‑then‑write non‑atomically. Annotating the service/repository would make the upsert atomic.
  • DB errors leak as 500: the UNIQUE email violation returns Spring's default error, not RFC 7807. Add @ExceptionHandler(DataIntegrityViolationException.class) returning 409 Conflict ProblemDetail.
  • H2 console 404: despite spring.h2.console.enabled=true, /h2-console is not served in this run — worth verifying the console autoconfiguration on Spring Boot 4.
  • Doc/code mismatch: the Chapter 4 deep‑dive describes maximum-pool-size: 10 etc., but no such Hikari tuning is present in application.properties (defaults apply).

Chapter takeaways. Spring Boot turns a URL + driver into a pooled DataSource automatically; JdbcTemplate gives explicit control (with a RowMapper) while JdbcClient offers a fluent, named‑parameter style over the same pool; schema.sql seeds structure; and profiles swap H2 for PostgreSQL without code changes. Remember to wrap multi‑statement work in @Transactional and to map data‑integrity errors to a proper HTTP contract.
