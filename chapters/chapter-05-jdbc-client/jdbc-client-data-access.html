1 · What this chapter covers

Chapter 5 refactors JDBC access onto the fluent JdbcClient API (Spring Framework 6.1+) and layers on transactions and multi‑table modeling. Two modules illustrate it:

  • customer/ (Maven, servlet/Tomcat) — single‑table CRUD via JdbcClient, named + positional parameters, automatic record mapping vs a custom RowMapper, and a portable update‑then‑insert upsert.
  • management/ (Gradle, reactive/WebFlux) — a four‑table domain (company, customer, address, communication) with foreign keys, a @Transactional service that writes all tables atomically, and functional endpoints (RouterFunction/HandlerFunction).

2 · Code walkthrough

The JdbcClient fluent pipeline

CustomerRepository.java (customer)

Every data‑access call is a builder chain: jdbcClient.sql(...).param(...).query(Customer.class).optional(). JdbcClient is created from the autoconfigured DataSource and wraps JdbcTemplate/NamedParameterJdbcTemplate behind one fluent surface.

Two parameter styles

CustomerRepository.java:31-48

.param("id", id) binds a named parameter (:id in SQL); .params(a, b, c) binds positional ? parameters. The repository mixes both — named for lookups, positional for the upsert SQL.

Automatic record mapping vs custom RowMapper

CustomerRepository.java:19-59

.query(Customer.class) auto‑maps columns to record components by name (zero boilerplate). findAll() instead passes an explicit lambda RowMapper to show the escape hatch for projections that don't match a record 1:1.

Database‑agnostic update‑then‑insert

CustomerRepository.java:27-42

Rather than dialect‑specific ON CONFLICT/MERGE, save() runs an UPDATE; if it affects 0 rows it falls back to INSERT. Portable across H2 and PostgreSQL.

Profiles: H2 (dev) vs PostgreSQL (prod)

application-dev.properties · application-prod.properties

spring.profiles.active=dev selects jdbc:h2:mem:customers; the prod profile targets jdbc:postgresql://localhost:5432/customers. schema.sql initializes the table in both.

Multi‑table domain & FK schema

management/schema.sql · model/*.java

Four tables with foreign keys: customer.company_id → company, address.customer_id → customer, communication.customer_id → customer. Each is a record; repositories follow the same JdbcClient pattern. CustomerDetailsDTO aggregates them for reads.

Declarative transactions

ManagementService.java:36-64

@Transactional createCustomerWithDetails(...) writes company → customer → address → communication in one atomic unit (FK order respected); a failure rolls all four back. @Transactional(readOnly = true) getCustomerDetails(...) reads and assembles the DTO.

Reactive functional endpoints

ManagementConfiguration.java:48-51 · reactive/ManagementHandlers.java

Instead of @RestController, routes are declared as a RouterFunction: route(GET("/api/v1/management/customers/{id}"), handlers::getCustomerDetails). The handler returns Mono<ServerResponse> — ok().bodyValue(dto) or notFound().

Observations & suggested improvements

  • Blocking JDBC on a reactive stack: management uses WebFlux/Netty, but JdbcClient is blocking — the handler runs JDBC on the event loop, which can starve it. Prefer a servlet stack for blocking JDBC, or offload to Schedulers.boundedElastic().
  • Both apps default to port 8080 — they can't run together unless one is moved (--server.port=8081).
  • POST returns 200, not 201 + Location in the customer module (returns the entity directly) — less RESTful than Chapter 3's controller.
  • DB errors leak as 500: duplicate email (UNIQUE) isn't mapped; add an @ExceptionHandler(DataIntegrityViolationException) → 409 ProblemDetail.
  • Upsert race: update‑then‑insert isn't atomic without a unique key + transaction; concurrent inserts of the same id could both see 0 rows. Fine for the demo, worth noting.

Chapter takeaways. JdbcClient unifies named/positional binding, automatic record mapping, and a fluent chain over the same pooled DataSource; the update‑then‑insert pattern keeps SQL portable; @Transactional makes multi‑table writes atomic; and functional endpoints offer a lightweight alternative to annotated controllers — just keep blocking JDBC off the reactive event loop.
